TokenOps Design Spec

Date: 2026-07-27 · Status: Draft for user review · Repo: tokenops (greenfield monorepo)

1. Problem

Token spend is fragmented across providers, coding agents, and machines. Vendor dashboards show invoices, not why tokens are wasted (frontier model for trivial tasks, full-document I/O, context bloat). There is no single ledger that spans apps and computers with actionable efficiency advice.

2. Goals

Product goals

  • Unified ledger: tokens and estimated cost by time, machine, app, model, and source.
  • Cross-machine: one account merges usage from every computer running the agent.
  • Inspection: request-level features (and optional content) power efficiency recommendations.
  • Open source + free tier: full stack OSS and self-hostable; hosted free tier is convenience, not a closed core.

Phase 1 success

  1. Credible multi-machine ledger (tokens + estimated $).
  2. Two capture paths: OpenAI-compatible local proxy + Claude Code adapter.
  3. Three high-confidence rule-based recommendations with estimated savings.
  4. Configurable privacy on the local agent (metadata always; content optional with TTL).

Non-goals (Phase 1)

  • Cursor, Gemini, browser-chat, or other adapters.
  • Multi-tenant orgs, SSO, invites, roles.
  • Automatic model routing (observe + advise only).
  • LLM-as-judge recommendations (hook-ready later).
  • Perfect provider billing parity.
  • Mobile apps or advanced BI.

Trust and privacy

  • Upstream provider API keys stay on the machine only. Never sent to cloud.
  • Cloud always receives metadata + derived features.
  • Content modes: off | local | cloud_ttl (short retention then drop).
  • Config: ~/.tokenops/config.toml.

5. Event model

Every observed call becomes a usage event. Optional payload is separate and TTL-scoped.

Usage event (always)

event_id, timestamp, machine_id, machine_name, app, provider, model, input_tokens, output_tokens, cost_usd (nullable estimate), latency_ms, session_id, features, has_content.

Features (always)

  • Prompt/response character lengths, message count
  • Large paste / code-fence / file-dump signals
  • Model tier (frontier / mid / small)
  • Session context-growth signal when session_id present

Idempotency & cost

event_id is a stable hash for upsert-safe ingest. Cost uses a shared price table with overrides; UI labels money as estimated.

6. Local agent

  • Proxy on 127.0.0.1:8787 — /v1/chat/completions required; embeddings optional.
  • Claude Code adapter — same event schema; hooks preferred, logs as fallback (implementation spike).
  • Outbox — SQLite with exponential backoff.
  • CLI — tokenops status, tokenops agent run, config init.

Provider keys never synced. Cloud down → queue grows; extract errors never break proxied requests.

7. Cloud API and dashboard

API

  • POST /v1/events — batch ingest (agent PAT)
  • GET /v1/aggregates, GET /v1/events
  • GET/POST /v1/recommendations
  • POST /v1/heartbeats, GET /health

Auth

Single-user; dashboard session (email/password or magic link); agent personal access token. No paid IdP required for self-host.

Dashboard screens

  1. Overview — tokens & est. $, top models, soft budget banner
  2. Explore — filters and event table
  3. Recommendations — tips, savings, dismiss
  4. Machines & sources — last seen, sync health
  5. Settings — price overrides, budget threshold

8. Rule engine (Phase 1)

  1. Frontier for trivial — high-tier model + tiny simple task → suggest smaller model.
  2. Full-document I/O — huge prompts/responses with dump signals → diffs/excerpts/chunks.
  3. Context bloat — rising session input with low new content → trim/summarize.

Shared implementation in packages/shared; dashboard recommendations are cloud-authoritative.

10–12. Data flow, security, testing

Flow: client → proxy/adapter → features + privacy → outbox → API → aggregates + rules → dashboard.

Security: provider secrets never leave the machine; TLS to cloud; content minimized with TTL GC; rotatable ingest tokens.

Testing: unit rules/features/cost/privacy; integration ingest/idempotency; proxy with mock upstream; ship verification against Railway/Compose, not localhost as the product gate.

13. Post–Phase 1 roadmap

  1. More adapters (Cursor, providers, browser exports).
  2. Optional LLM-as-judge.
  3. Budget alerts (email/webhook).
  4. Multi-user / team.
  5. Opt-in auto-routing later.

14. Implementation notes (not product ambiguity)

  • Claude Code capture mechanism: spike in first implementation PR.
  • Hono vs Fastify: pick in implementation plan.
  • MIT vs Apache-2.0: set at license file creation.
  • Password vs magic-link: simplest self-host-friendly option in plan.
